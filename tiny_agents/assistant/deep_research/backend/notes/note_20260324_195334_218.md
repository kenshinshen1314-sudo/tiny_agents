# 任务 1: OpenClaw背景梳理

任务概览：梳理OpenClaw工具的基本信息、功能定位、技术架构
系统提示：了解OpenClaw是什么、谁开发、主要用途、工作原理
来源概览：官方文档、GitHub仓库、技术博客、安全社区讨论

## 关键发现

### 1. 架构设计：Gateway为中心的信任边界
OpenClaw采用单一Gateway进程作为控制平面，默认绑定127.0.0.1:18789端口，所有消息通道（WhatsApp/Telegram/Discord等）通过WebSocket汇聚。Gateway是信任边界核心， inbound消息视为不可信输入，未知联系人需配对审批。这种设计将攻击面集中在单一进程，Gateway被攻破即意味着全系统沦陷。

### 2. 本地存储模型：明文文件的风险敞口
所有对话、记忆、技能以Markdown文件形式存储在~/.openclaw/目录，包括MEMORY.md、SOUL.md、openclaw.json等。无加密保护，任何获得文件系统访问权限的进程均可读取敏感数据。配置验证虽严格，但存储层缺乏机密性保障，宿主机 compromised 后数据完全暴露。

### 3. 插件架构：2026年重构后的供应链风险
PR #661将模型提供商解耦为独立npm包动态加载，支持20+ AI提供商。依赖隔离带来版本自主权，但也引入供应链攻击向量。参考2026年2月Cline CLI事件（GHSA-9ppg-jx86-fqw7），postinstall钩子可静默安装恶意组件，OpenClaw的插件加载机制存在类似风险。

### 4. 设备配对机制：身份验证的双刃剑
所有WS客户端需设备身份配对，新设备需审批后获token。本地连接可自动审批提升体验，但非本地连接需显式批准。签名payload v3绑定platform+deviceFamily，元数据变更需重新配对。然而，若攻击者获取已配对设备token，可绕过审批机制持久化访问。

### 5. 部署模式多样性：安全基线不一致
支持四种部署：Mac mini本地、隔离VPS、Cloudflare Moltworker、Docker Model Runner。不同场景安全基线差异大——本地部署依赖主机安全，VPS需额外加固，serverless依赖Cloudflare信任模型。用户往往选择最便捷而非最安全方案，导致实际安全 posture 低于设计预期。
